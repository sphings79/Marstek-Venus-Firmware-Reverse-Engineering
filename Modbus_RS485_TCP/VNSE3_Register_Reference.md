# VNSE3 – Modbus register reference (Venus E3)

> 🇩🇪 Deutsche Version: [VNSE3_Register_Referenz_de.md](VNSE3_Register_Referenz_de.md)

Complete, code-verified reference of all 584 registers of the Venus E3 Modbus map (Control E3 151, BMS E3 115, Micro E3 119). Every register was traced from its handler or descriptor entry to the origin or consumer of its value and checked for functionlessness; the column *Same as D* compares with the verified Venus D map (`VNSD_Register_Reference.md`). The single source of truth is `VNSE3_Register_Map_Final_generated.csv` (columns `status_E3`, `gleich_wie_D_E3`, `beweisstand_E3`, `einheit_skala_E3`, `ziel_E3`, `leseeffekt_E3`, `befund_E3`, `gefahr_E3`, `suite_empfehlung_E3`); this document is generated from it.

Status values as in the D reference: **FUNCTIONAL**, **CONDITIONAL** (only in a special mode / after another write), **NO_OP**, **FUNCTIONLESS** (proven for every device whose firmware is available), **UNKNOWN** (open). Counts: FUNCTIONLESS 320, FUNCTIONAL 190, CONDITIONAL 64, NO_OP 10.

Physical value = raw value × factor (column *Unit / scale*). Registers below 40000 are read-only. *Same as D*: yes = identical meaning, scale and status as on the Venus D; partly = same register but different details (constants, values, origin); no = different behaviour or status.

## 1. Behaviour that applies to many registers

- **The Control is a near clone of the Venus D Control 151** (93.4 % of the image identical; `Write_Handler` is instruction-identical, the Modbus descriptor table has the same 246 descriptors with the same types; only the RAM source pointers are 16 bytes lower). Removed compared with D: PV/MPPT, stack/parallel features, export limiter, surplus feed-in. The power-class selector offers 600/800/2500 W and changes only the Control's maximum-discharge value, so a Modbus write to 44003 bypasses the class.
- **One fixed battery pack (stated by the owner, hardware fact):** the E3 BMS 115 sends frames for pack 1 only (its only caller passes the constant 1; the bound `pack_id < 10` is never exercised), the Control keeps 8 records of 0x60 bytes but fills only record 0. Registers of packs 2–7 (34100–34633) always read 0. Packs count from 1, record indices from 0.
- **The E3 BMS is a separate code base** (17.7 % identical to D 118; AFE KA495XX, 16 cells, 4 cell NTCs, current scale 100 A). The SOC registers 34002, 37005 and 32104 carry a float SOC that the BMS integrates from the micro's battery-power telemetry, not a coulomb counter. 34017/30106 carry the battery profile (low byte) and the MOS-off bits (high byte).
- **The E3 micro (STM32G474, 73.5 % identical to D 116) has no PV/MPPT stage and no class-2 node:** every register whose only target is the missing MPPT/class-2 hardware is proven functionless because the firmware of all three internal devices is available. Class-4 CAN commands 0x08, 0x0A, 0x14, 0x17 are new compared with D; 0xCC is not needed.
- **Power limits:** user limit 2500 W (the micro uses 3000 W internally); a written 0 in 44002/44003 is stored in the micro's EEPROM and reloaded without range check. New on the E3: the Control polls the micro's limits (CAN 0x14) about every 30 s and the 44002/44003 read-back shows the micro's real values.
- **Serializer and pair rules of the Control are the same as on D:** signed values the firmware divides by 10/100 lose their sign (only 32101); two-register values must be read as a pair; Modbus TCP exception frames carry MBAP length 4 with only 3 bytes following; the Wi-Fi state URC string mismatch (space vs underscore) exists as well.
- **Identifiers:** the runtime model id is `VNSE3-0` (device model register 31001–31003, BLE name `MST_VNSE3_…`); `VNSEE3-0` appears only in the OTA/boot checks. The communication module is the same FC41D with the same firmware image as the D.
- **Unproven hardware facts:** whether the RJ45/CH395 port is fitted, whether the cell-balancing hardware is populated (the balancing code is present and active), and who sends the Pylontech-style standard CAN frames 0x305/0x300/0xCF (no E3 firmware does).

## 4. Open questions

- Purpose of the 4000 mV report clamp (signal 'full' to an external inverter?).
- What battery/cell variants the five table sets represent (factory setting per cell supplier?).
- Exact IWDG timeout (LSI frequency of the N32G45x) and BMS boot time vs the Control's 5 s window - only a live test can show whether 0xAA ever arrives in time.
- Tick unit of g_appTickMs in Bat_Mode3RoundRobinTimer (named ms, but the 0x1C20/0x3840 timeouts only make sense as seconds as on D).
- Timing: the micro's level-1 reset (g_emsDispatchSeq) is deferred ~10 dispatcher cycles while the Control reboots and sends 0x05 at boot; both lead to a micro reset, the code order (Inv_BuildTelemetryBlock.c:93 before :106) suggests the factory reset wins only if it fires before the 0x05 arrives (D has the same structure; not proven).
- Initial value of the shadow in the .data image before the first 0x14 reply (D analysis: 0); not decompressed here.
- Live check recommended: read 44002/44003 on an E3 after a reboot without writing (expect the micro values within ~30 s).
- Mapping of the renumbered PFC test codes 0x14/0x16 in the state-0 jump table of Ctrl_MainControlIsr (CCM) not traced.
- Which physical battery/cell variant each profile set describes and which profile is the factory value of a shipped E3 (EEPROM 0x258 content).
- Bootloader (0x08000000-0x080047FF) not available: assumed not to configure PB10.
- Physical placement of the CH12 / CH5 NTCs on the E3 inverter board (code only names them radiator 1 / radiator 2).
- Polarity of PB1 (1 = fault or 1 = OK) - hardware question.
- Only a non-Marstek device on the CAN bus could still send 0x1807AA0n; no such device is known for the E3.
- Physical meaning of micro control states 0xCC and 0xD4..0xD6 (backup branch states).
- FC41D atcmd_QGETWIFISTATE error path when not associated: taken from the A4/H1 reading of the FC41D export (helper FUN_000269d0 name not confirmed).
- Hardware: is the CH395/RJ45 port populated on the Venus E 3.0? The complete CH395 driver is compiled in, but firmware cannot show the board population; without it the block stays 0.
